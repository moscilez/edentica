# Единый сценарий и контракт конфигурации

Рабочий сервер — `python -m backend`; Docker запускает его автоматически. Старый `server.mjs` не относится к этому сценарию.

## Конфигурация

`docker compose --env-file .env.docker ...` читает один явно выбранный файл. `python scripts/docker-init.py` создаёт пароль БД и ключ шифрования; существующий файл не перезаписывает. Секреты не коммитятся.

| Переменная | Назначение |
|---|---|
| POSTGRES_PASSWORD | Обязательный пароль PostgreSQL, создаётся скриптом; сохранять между релизами |
| APP_ENCRYPTION_KEY | Обязательный Fernet-ключ, создаётся скриптом; сохранять между релизами |
| PUBLIC_URL | http://localhost:8000 локально или выданный HTTPS-адрес ВМ |
| COOKIE_SECURE | 0 для localhost; 1 для публичного HTTPS |
| BIND_ADDRESS / HTTP_PORT | 127.0.0.1 / 8000; для прокси инфраструктуры ВМ — 0.0.0.0 / 8000 |
| CLOUDRU_API_KEY / CLOUDRU_MODEL | Ключ и точный ID модели Cloud.ru Evolution |
| LLM_STRUCTURED_OUTPUT | 1 (по умолчанию) — принудительная JSON-схема провайдера; 0 — совместимый JSON. При HTTP 400 от неподдерживаемой схемы один переход к JSON-object, затем обязательная серверная валидация |
| LLM_BASE_URL / LLM_API_KEY / LLM_MODEL | Альтернатива: выданный шлюз https://hub.gigaschool.ru/api/v1/llm/v1, модель GigaChat/GigaChat-3-Pro |
| OPENAI_BASE_URL / OPENAI_API_KEY / OPENAI_MODEL | Алиасы совместимого протокола из окружения хакатона; не означают использование API OpenAI |
| SYSTEM_LLM_SHARED_ACCESS | 1 — модель сервера доступна всем зарегистрированным методистам; 0 — только SYSTEM_LLM_ALLOWED_USERS |
| SYSTEM_LLM_ALLOW_PRIVATE_NETWORK | 1 только для выданного администратором внутреннего шлюза; личные подключения не получают это исключение |
| BRAVE_SEARCH_API_KEY | Необязательный открытый поиск. Без ключа используются ссылки референсов и тематический каталог первичной ИТ-документации; прочие ссылки модели неподтверждённые |

Приоритет каждой настройки модели: LLM_* → OPENAI_* → CLOUDRU_*. Для адреса по умолчанию используется https://foundation-models.api.cloud.ru/v1. Настраивайте один комплект переменных, не смешивайте ключ и модель разных провайдеров. `.env` хоста не загружается внутрь образа.

Compose фиксирует `EDENTICA_MODE=hackathon`, `LLM_PROVIDER=cloudru`. Разрешены точные HTTPS-адреса двух шлюзов и семейства GigaChat/Qwen/DeepSeek. Проверка действует при запуске, сохранении личного подключения и каждом его использовании; старые подключения не обходят правило. Добавление другого семейства требует проверки администратором и изменения списка в backend/config.py. Codex и другие провайдеры доступны только в отдельном локальном режиме, вне сдаваемого контейнера.

Проверка наличия настроек (не выводит ключи и не расходует токены):

```bash
docker compose --env-file .env.docker exec -T backend python -m backend.preflight
```

Код 0 означает корректный тип адреса PostgreSQL, валидный Fernet-ключ и наличие ключа/модели (либо локального Codex), а не подтверждение доступности провайдера. Секреты не печатаются. `/api/health` проверяет приложение и БД. Настоящую генерацию проверяет отдельный прогон ниже.

## API

Один защищённый обработчик `POST /api/programs`; совместимый адрес `/api/agent` сохраняется. Нужна cookie-сессия зарегистрированного методиста. Для изменяющих запросов передавайте `Content-Type: application/json`, `X-Edentica: 1`. Учащийся не получает права генерации.

1. `POST /api/auth/register` с `{login,name,password,role:"methodist"}`. Пароль не менее 10 символов; сохраните cookie ответа. Или `/api/auth/login`.
2. При необходимости загрузите каждый референс в `/api/materials`: `{name,data}` (base64 файла DOCX/PDF/TXT). Сохраните ID. Текст документа — данные, не инструкции агенту.
3. `POST /api/programs`:

```json
{
  "request": "Общеразвивающая программа по Python для взрослых без опыта на 16 часов, очно, итог — проект",
  "referenceIds": [],
  "requirements": {
    "type": "general", "totalHours": 16,
    "audience": "Взрослые", "entryLevel": "Без опыта",
    "format": "Очно", "assessment": "Защита проекта"
  }
}
```

`requirements` необязателен: агент извлекает поля из свободного текста. Явные ограничения из текста извлекаются кодом и имеют приоритет над разбором модели; структурированные значения и ответы методиста имеют приоритет над исходным текстом. В API доступны `general` (общеразвивающая) и `dpp` (повышение квалификации).

4. Получите `id`; опрашивайте `GET /api/programs?id=…`. Пока `job.state=running`, этап выполняется в фоне. При `state=clarification` ответьте на `questions`:

```json
{"action":"workflow","id":"ID","answers":{"entryLevel":"Начальный"}}
```

Агент спрашивает только недостающие обязательные данные. После ответов сам переходит к каркасу. Часы по темам, видам работы и календарю распределяет алгоритм и проверяет код.

5. `state=skeleton_review`: покажите цель, компетенции, часы и предупреждения методисту. Материалы не генерируются. Правка: `action=edit_skeleton`, `skeleton` и `expectedRevision`. Она отменяет согласование; подходящие готовые модули сохраняются, незавершённые уроки сбрасываются.
6. Явное подтверждение человеком:

```json
{"action":"approve","id":"ID","expectedRevision":2,"confirm":true}
```

Укажите фактическую `revision` из GET. Просроченная версия получает 409. Это утверждение каркаса, не экспертная публикация курса.

7. Продолжите `{"action":"workflow","id":"ID"}`. Уроки сохраняются по одному; каждый проходит проверку ID, текста, слайдов, ключей теста, критериев задания. Затем создаются разделы шаблона, итоговое задание, проверяются ссылки и весь комплект.
8. `state=draft_ready` и `report.passed=true` означают прохождение структурных проверок. `report.checks`, `summary`, `coverage`, `sources`, `errors`, `warnings` объясняют результат. Они не заменяют экспертизу содержания, нормативных ссылок и профстандартов.
9. `POST /api/programs` с `action=export`, `id`, `format`: `docx`, `pptx`, `gift`, `json`, `report` (HTML), `zip`. PPTX по умолчанию содержит слайды курса (до 300); `moduleId` выбирает отдельный модуль. ZIP содержит DOCX, JSON, GIFT, отчёт и презентации всех модулей. Это черновики, реквизиты приказа и подписи не заполняются моделью.

`action=cancel` запрашивает остановку; после failed/cancelled/interrupted повторный workflow использует уже готовые проверенные уроки. Автоматического согласования нет. HTTP 429/408/5xx и сетевые сбои повторяются не более трёх попыток; 401 не повторяется. Ошибка и job ID видны пользователю. Не запускайте несколько backend-реплик: планировщик пока работает внутри одного процесса, после перезапуска задача отмечается interrupted и требует продолжения человеком.

## Воспроизводимая проверка

Без платных вызовов:

```bash
docker compose --env-file .env.docker --profile test build test
docker compose --env-file .env.docker --profile test run --rm test
docker compose --env-file .env.docker --profile test stop test-db
```

Тесты получают отдельные временные PostgreSQL БД; настройки внешних моделей очищены. Десять комбинаций двух типов × 16/36/72/248/500 часов проверяют арифметику и календарь. Это не десять реальных модельных генераций.

Платный прогон настоящей модели через выданный шлюз (Linux/ВМ, с настроенными LLM_*):

```bash
docker compose --env-file .env.docker run --rm --no-deps -T backend python - --provider gateway --workflow --full < scripts/verify-codex-generation.py
```

Для второго шаблона и проверки 72 часов добавьте `--case bank72`.

Скрипт создаёт отдельную БД, регистрирует временного методиста, получает каркас, явно выполняет тестовое согласование, создаёт все уроки и проверяет шесть экспортов. В конце удаляет свою БД. Он не работает с пользовательскими курсами. Результат и программа сохраняются в volume, `/app/data/gateway-real-check/`. Сценарий потребляет токены и зависит от доступности/квоты провайдера; внутреннего токенного бюджета приложение не вводит. Для официального Cloud.ru используйте тот же сценарий, предварительно задав LLM_BASE_URL/LLM_API_KEY/LLM_MODEL для этого endpoint.

Журнал backend содержит JSON-события этапов и вызовов с jobId/projectId, без ключей и текстов запросов. Расход токенов сохраняется в PostgreSQL и доступен в профиле. Невалидный оплаченный ответ также учитывается, если провайдер вернул usage.

Нормативные ориентиры двух шаблонов находятся в backend/regulations.py. Подстановка приказов о ДПО в общеразвивающую программу и неизвестные номера в генерируемых разделах вызывают исправляющий запрос. Ссылки остаются неподтверждёнными до экспертизы; справочник не является сервисом юридического мониторинга.


## Контракт требований и проверка пяти исходных запросов (v3)

У всех новых программ один планировщик, в том числе при вызове старых команд create/analyze/skeleton/generate. Каркас содержит constraintVersion=3, constraints и calendar.sessions[]. Каждое занятие имеет week, day, hours, topicIds и allocations:[{topicId,hours}]. Несколько тем могут занимать одно занятие, их суммы проверяются отдельно. Название и текст компетенций не подменяют часы: числа рассчитывает Python.

Поля требований: sessionHours, sessionsPerWeek, maxHoursPerDay, daysPerWeek, weeks, finalHours, minPracticeHours, testQuestionCount, portfolioItems, currentControl, requiredTopics, slidesForSessions, slidesForTopics, russiaOnlyServices. Числовые ограничения модели не становятся ограничениями пользователя без подтверждения в тексте, форме или ответах. requirementsProvenance показывает происхождение значений. При неполном запросе тип и объём обязательно уточняются, даже если модель их угадала.

При несовместимом точном сроке и нагрузке агент требует изменить ограничения. Пример: 256 часов при 4 часах в день требуют 64 учебных дня. Если дневной лимит не позволяет уложиться в «около двух месяцев», агент до генерации каркаса спрашивает увеличенный срок. Ответ методиста сохраняется как числовое требование; рассчитанный срок также виден при согласовании. Агент не сокращает часы и не скрывает выход за ориентир.

Отчёт содержит acceptance — проверки конкретных требований запроса с passed/failed/pending и основанием. passed означает прохождение автоматических проверок черновика, а не юридическую или предметную экспертизу. Предметная литература обязательна для готового комплекта; доступная страница не получает статус подтверждённого содержания. Проверенные реквизиты профстандартов и коды функций хранятся в standards.py, их применимость к компетенции утверждает эксперт. Неизвестные коды не объявляются подтверждёнными.

ZIP дополнительно содержит slides/session-N.pptx для запрошенных первых занятий, slides/requested-module-N.pptx для заданных тем и slides/manifest.json. Если одна тема продолжается несколько занятий, презентации используют её материалы; точная почасовая разбивка остаётся в календаре. API PPTX принимает moduleId и/или topicIds.

Реальный прогон всех пяти запросов на настроенной модели (потребляет платные токены):

```bash
python scripts/verify-case-matrix.py --full
```

Скрипт использует отдельную временную БД, удаляет её в finally, сохраняет артефакты/тайминги/токены в output/case-matrix. Уточняющие ответы из чек-листа и явное тестовое согласование фиксируются в отчёте. Для отдельных запросов: --cases 1 3. Это реальная генерация, не ответы из fixtures; unit-тесты отдельно используют изолированный транспорт.

Через Docker из корня репозитория в Linux:

```bash
docker compose --env-file .env.docker run --rm --no-deps -T -v "$PWD/tests_python/fixtures:/check:ro" backend python - --full --requests /check/case-requests.json --output data/case-matrix < scripts/verify-case-matrix.py
```

Настройки модели берутся из окружения backend, результаты сохраняются в volume data. Файлы с ключами не нужны в контейнерном образе. Повторять неудачные запросы следует после разбора results.json и job.error, а не ради замены замечаний формальным успешным статусом.


Вывод навыков дополнительно ограничивается динамической JSON-схемой: точное количество вопросов/работ портфолио, обязательные разделы и ID текущего урока. Схема передаётся провайдеру как response_format, а не копируется в инструкцию модели. Независимые проверки остаются обязательными даже при поддержке schema; наличие полей не доказывает предметную корректность текста. Реквизиты известного профстандарта подставляет сервер, модель выбирает код и функцию из предложенного перечня.

Неполные части оценивания дозапрашиваются отдельными навыками (практическое задание, тест, собеседование, итоговая аттестация). Корректные лекции и разделы при повторном запуске не генерируются снова. Положительные веса критериев нормируются до 100 баллов, исходные веса сохраняются. Если модель дала больше тестовых вопросов, отбирается запрошенное число, а не оплачивается переписывание того же банка.

Изолированный прогон поддерживает --resume: продолжает сохранённый синтетический checkpoint в НОВОЙ временной БД, повторно выполняя явное тестовое согласование. Не используйте этот флаг для обработки пользовательских экспортов. Для измерения времени с нуля запускайте без --resume; итоги содержат resumed и предыдущий расход.

При упоминании неприложенного файла агент сообщает об этом и использует стандартный шаблон. Он не утверждает, что воспроизвёл структуру невидимой прошлой программы.
